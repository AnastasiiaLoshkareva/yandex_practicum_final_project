 # SmartScore: батч-инференс высокого спроса на объявления

Проект предсказывает для объявлений об аренде жилья (10 городов: Amsterdam, Chicago, Los Angeles, London, Lyon, Munich, New York, Paris, Toronto, Vienna) бинарный признак `is_high_demand` («спрос на объект значимо выше, чем у похожих объявлений»). Обучение и исследование выполнены в Jupyter-ноутбуках, батч-инференс на тестовом срезе автоматизирован в Apache Airflow, результат записывается в таблицу PostgreSQL.

---

## 1. Описание задачи и работы DAG

**Бизнес-задача.** Находить объявления с высоким спросом, чтобы приоритизировать работу с листингами (отзывы, заполнение карточки, цена).

**Что делает DAG `listing_scoring_dag`.** Дата инференса определяется автоматически как максимальная `snapshot_date` в `final_project.smartscore_test_snapshot`. Задачи сгруппированы по `TaskGroup`:

| Группа | Задача | Что делает |
|--------|--------|-----------|
| `load_data` | `check_model_on_s3` | Проверяет наличие в S3 модели, `catboost_meta.json` и `preprocess_artifacts.json`; при отсутствии DAG падает до обработки данных |
| `load_data` | `build_and_upload_features` | Читает тестовый срез, календарь и отзывы из PostgreSQL (`PostgresHook`), собирает таблицу, рассчитывает признаки на дату инференса (`preprocess.py`) и сохраняет их в S3 |
| `inference` | `make_prediction` | Скачивает признаки и модель CatBoost из S3, считает вероятность `proba` и класс `pred` по порогу из `catboost_meta.json`, сохраняет результат в S3 |
| `save_results` | `save_to_db` | Записывает результат в `public.smartscore_predict` |

Через XCom передаются только маленькие словари (дата, число строк, ключ в S3), таблицы хранятся в S3.

**Идемпотентность.** Если за дату инференса в `public.smartscore_predict` уже есть строки, повторный запуск ничего не добавляет. Новые строки добавляются только для новой даты.

**Логирование.** В логах видны дата инференса, число выгруженных строк, найденные в S3 файлы, доля положительного класса, число записанных строк и пропуск вставки при повторном запуске.

## 3. Сборка обучающей таблицы и целевой переменной

**Как собирали таблицу.** Данные лежат в PostgreSQL (схема `final_project`) отдельно по каждому из 10 городов: `{city}_listings`, `{city}_calendars`, `{city}_reviews`.

* `listings`: таблицы всех городов объединены через `UNION ALL` с добавлением колонки `city`, получено 661 425 строк и 65 колонок. В таблицах несколько снимков одного объявления (отличаются цена, число отзывов, рейтинг), поэтому по ключу `(city, id)` оставлена одна строка, удалено 297 341 дубль. Итого 364 084 объявления.
* `calendars`: агрегация выполнена в БД на уровне объявления (доля доступных дней `calendar_availability_rate`, средние ограничения по ночам), 327 717 объявлений. Агрегат на стороне БД выбран, потому что полная календарная таблица очень большая.
* `reviews`: в БД для каждого объявления берутся 10 последних отзывов за год до последней даты отзывов города. Считаются средняя длина отзыва (`avg_recent_comment_len`) и склеенный текст (`concat_recent_comments`), 185 123 объявления.
* Таблицы соединены с `listings` по `id` через `LEFT JOIN`: объявления без календаря или отзывов остаются, пропуски сохраняются как `NaN`.

**Медианы по сегментам.** Для каждой пары `city` + `room_type` посчитаны медианы `numeric_of_reviews_ltm` (отзывы за год), `price` и `review_scores_rating` (пропуски при расчёте медианы игнорируются). Сегмент «город + тип жилья» выбран, чтобы сравнивать объявление с похожими, а не со всем рынком (цены и число отзывов в разных городах несопоставимы).

**Целевая переменная `is_high_demand`.** Рассчитаны `price_ratio = price / median_price` и `rating_ratio = rating / median_rating`. Целевая переменная равна 1, если одновременно:

* отзывов за год больше медианы сегмента;
* `price_ratio >= 1` (цена не ниже рынка);
* `rating_ratio >= 1` (рейтинг не ниже рынка);

и 0 во всех остальных случаях.

**Защита от утечки данных.** Из признаков удалены все колонки, из которых считается цель: `numeric_of_reviews_ltm`, `price`, `review_scores_rating`, `median_reviews_ltm`, `median_price`, `median_rating`, `price_ratio`, `rating_ratio`. Идентификатор `id` и сырые даты удалены. Колонка `city` использовалась только для расчёта цели и в признаки не входит. Из календаря исключены поля с фактической заполняемостью будущих дат (`calendar_booked_days_365`) и будущие цены.

## 4. EDA

**Пропуски.** `price` отсутствует у 60.7% объявлений, `review_scores_rating`, `first_review`, `last_review` у 24.2% (объявления без отзывов), `host_response_time` у 41.8%, `beds` и `bathrooms` у 46% (до обработки). Пропуски не заполнялись средним или медианой, потому что часто сами несут информацию: у объявлений без указанных ванных доля высокого спроса 0.15% против 11.7% у остальных. Количество ванных восстановлено из `bathrooms_text` (пропусков было 114 104, осталось 373).

**Аномалии.** Значение `maximum_nights = 2 147 483 647` оказалось технической заглушкой и заменено на `NaN`. У `minimum_nights` есть кластер около 365 ночей (долгосрочная аренда) и хвост до 1 125. Значение `host_listings_count = 5230` принадлежит одному крупному оператору, оставлено как есть.

**Связь признаков с целью.**

* Суперхосты дают около 23% высокого спроса против 3.6% у остальных. Чем быстрее хост отвечает, тем выше доля (около 12–13% при ответе в течение часа и нескольких часов, около 2% при ответе в течение нескольких дней, 2.6% у группы с пропуском).
* Закрытый календарь (доля доступных дней 0) даёт около 1% против 7% в среднем.
* Доля растёт с вместимостью (`accommodates`) и числом кроватей и падает с минимальным сроком аренды: 2–4 ночи дают около 10–12%, от 28 ночей около 1–2%.
* Коэффициент Phi_K с целью не превышает 0.21–0.23, ни один признак по отдельности цель не объясняет.

**Мультиколлинеарность.** По Phi_K найдены дубли (0.80 и выше): `calendar_avg_min_nights` и `minimum_nights`, `host_listings_count` и `host_total_listings_count`, `calendar_availability_rate` и `availability_eoy`, `host_response_rate` и `host_response_time`. Удалены `calendar_avg_min_nights`, `calendar_avg_max_nights`, `availability_eoy`, `host_response_rate`, `calculated_host_listings_count`, `host_listings_count`, а также слабые `neighbourhood_cleansed` и сырой `property_type`.

**Вывод.** Для прогноза нужна комбинация признаков: календарь и активность хоста, параметры жилья и правила бронирования, поэтому выбраны древовидные модели.

## 5. Признаки и обработка текста

**Итоговый набор:** 31 признак: 7 категориальных, 2 текстовых, 22 числовых.

* Категориальные: `room_type`, `host_response_time`, `host_is_superhost`, `host_identity_verified`, `instant_bookable`, `host_has_profile_pic`, `property_type_top`. Пропуски кодируются категорией `Missing`; `property_type_top` оставляет 20 самых частых типов жилья, остальные `Other`.
* Новые числовые признаки: `days_since_last_review`, `review_span_days`, `host_tenure_days` (даты переведены в количество дней), `calendar_closed`, `is_long_stay` (минимум от 28 ночей), `guests_per_bedroom`, `guests_per_bathroom`, `amenities_count` (число удобств по запятым, оценка приблизительная).
* Даты считаются относительно опорной даты. При обучении опорной датой служит последний отзыв города, при инференсе дата батча.

**Обработка текста.** Из названий (`name`) и склеенных свежих отзывов получены строки `filtered_name` и `filtered_sentences`. Шаги: нижний регистр, удаление знаков препинания и лишних пробелов, разбиение на слова, удаление стоп-слов. Отзывы многоязычные, поэтому использован список стоп-слов восьми языков (английский, французский, немецкий, испанский, нидерландский, итальянский, португальский, русский; 1 501 слово из NLTK). Пропуски в тексте заменяются пустой строкой.

**Кодирование.** Масштабирование не применяется: все модели древовидные. Для Random Forest и LightGBM категории кодируются `OrdinalEncoder`, текст `TfidfVectorizer(max_features=100)` отдельно для каждого текстового признака. Для CatBoost категории передаются строками, текст как `text_features` (нативная обработка). Пропуски в числовых признаках оставлены: в Random Forest, LightGBM они заполняются `-1` как маркер «нет данных» внутри пайплайна, в CatBoost остаются `NaN`. Преобразования обучаются только на обучающей выборке (внутри пайплайна на каждом фолде).

## 6. Моделирование и эксперименты

**Разделение.** Данные разделены 80/20 со стратификацией по цели (`random_state=42`): обучающая выборка 226 018 объектов, тестовая 56 505, доля класса 1 около 7.04% в обеих. Тестовая выборка использовалась один раз, для финальной оценки.

**Метрики.** Класс редкий (около 7%), поэтому основной метрикой выбрана PR-AUC (не зависит от порога), дополнительно ROC-AUC, F1, Precision и Recall. Все модели сравнивались на одинаковой 5-кратной стратифицированной кросс-валидации. Для моделей с учётом дисбаланса использованы веса классов.

| № | Модель | PR-AUC | ROC-AUC | F1 | Precision | Recall | Примечание |
|---|--------|--------|---------|----|-----------|--------|------------|
| 1 | Random Forest (baseline) | 0.550 | 0.947 | 0.260 | 0.760 | 0.157 | порог 0.5 |
| 2 | LightGBM | 0.630 | 0.959 | 0.494 | 0.334 | 0.949 | порог 0.5, TF-IDF для текста |
| 3 | CatBoost | 0.657 | 0.962 | 0.538 | 0.381 | 0.913 | порог 0.5, нативный текст |
| 4 | CatBoost + Optuna | 0.615 | 0.956 | – | – | – | хуже базовой настройки |
| 5 | CatBoost, порог 0.782 | 0.657 | 0.962 | 0.613 | 0.549 | 0.694 | порог по максимуму F1 на OOF |

**Выбор модели.** Лучший по PR-AUC CatBoost (на 0.027 выше LightGBM). Подбор гиперпараметров (Optuna, 8 испытаний на подвыборке 20 000 строк, 3 фолда) на полной обучающей выборке дал PR-AUC 0.615, хуже стандартных настроек (0.657), поэтому оставлена базовая конфигурация: 500 итераций, `auto_class_weights='Balanced'`.

**Порог.** При пороге 0.5 модели с балансировкой дают высокую полноту, но низкую точность, поэтому порог подобран по out-of-fold-предсказаниям (максимум F1): 0.782. Порог сохранён вместе с моделью и признаками в `catboost_meta.json`.

## 7. Оценка и бизнес-интерпретация

**Метрики на тесте (порог 0.782).**

| Метрика | Значение |
|---------|----------|
| PR-AUC | 0.654 |
| ROC-AUC | 0.962 |
| Precision | 0.545 |
| Recall | 0.691 |
| F1 | 0.610 |

Значения почти совпадают с кросс-валидацией (PR-AUC 0.657, F1 0.613), признаков переобучения нет. Из 3 975 объявлений с высоким спросом модель находит около 69%, при этом около 55% её срабатываний верны (примерно в 8 раз лучше случайного выбора).

**SHAP-анализ.** Самые важные признаки: `avg_recent_comment_len` (1.96), `beds` (1.59), `review_span_days` (1.04), `days_since_last_review` (0.93), `filtered_name` (0.87). Высокий спрос связан со свежими и содержательными отзывами, недавней активностью и большим числом кроватей. Отсутствие отзывов и данных о кроватях сильно снижает оценку. Координаты (`latitude`, `longitude`) играют роль города.

**Что это значит для бизнеса.** На спрос больше всего влияет «живость» объявления: наличие свежих отзывов и заполненность карточки. Для листингов с низким скором полезно запрашивать отзывы, заполнять характеристики жилья и обновлять объявление. Модель подходит для приоритизации листингов, а не для автоматических решений.

**Рекомендация.** Внедрять как пилот для приоритизации листингов с контролем человека, регулярно отслеживать долю положительных предсказаний, долю пропусков в признаках отзывов и качество по городам, и переобучать модель при смене данных.

## 8. Запуск и настройка

**Окружение.** DAG рассчитан на Airflow 2.9.2 и Python 3.12. Версии библиотек зафиксированы в `requirements.txt`, версия `catboost` совпадает с версией, на которой обучена модель (1.2.10). Модель `.cbm` и `catboost_meta.json` читаются без `joblib`, поэтому не зависят от версий `numpy` и `pandas`.

**Airflow Connections** (в коде нет паролей и ключей):
* используется .env:
  - для БД: DB_USER, DB_PASS, DB_HOST,  DB_PORT, DB_NAME
  - для S3: S3_BUCKET, S3_ENDPOINT_URL, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
* `postgres_raw`: подключение к PostgreSQL (host, port, schema, login, password);
* `s3_features`: параметры в `Extra` (`bucket`, `endpoint_url`, `aws_access_key_id`, `aws_secret_access_key`).

**Airflow Variables** (есть значения по умолчанию):

* `smartscore_model_prefix` (по умолчанию `models/high_demand_catboost/v1/`);
* `smartscore_work_prefix` (по умолчанию `smartscore/inference/`).

**Запуск.**

1. Положить файлы из папки `dags/` в каталог DAG Airflow.
2. Убедиться, что в S3 лежат три файла модели (задача `check_model_on_s3` проверит это сама).
3. Запустить DAG `listing_scoring_dag` вручную (`schedule=None`).
4. Проверить результат:

```sql
SELECT inference_date, COUNT(*), AVG(pred) AS share_high_demand
FROM public.smartscore_predict
GROUP BY inference_date;
```

Число строк должно совпадать с числом объявлений тестового среза, а доля класса 1 не должна быть ни 0, ни 1.

**Безопасность.** Секреты (пароли БД, ключи S3) хранятся только в Airflow Connections, в локальном `.env` (он добавлен в `.gitignore`), в репозиторий они не попадают.
