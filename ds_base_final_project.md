## 0. Заметки со встреч и контекст задачи

Объект наблюдения - Объявления по аренде жилья на платформе StayAI

Целевая переменная - Оценка ожидаемого уровня спроса объявления
	компоненты оценки: 
	- востребованность жилья на рынке
	- конкурентная цена
	- опыт проживания гостей — рейтинг

Решаемая проблема - неактуальные объявления влияют на уменьшение конверсии и репутацию платформы, новые объявления имеют риск быть незамеченными, что влияет на потенциальные потери прибыли

Ожидаемый эффект - различие новых от старых, потенциально сильных от старых объявлений для повышения конверсии

Частота подсчета предсказаний - переобучение модели 1 раз в месяц

Хранение и передача полученных предсказаний - загрузка результатов предсказаний в поисковый индекс, модель сериализуется и сохраняется в S3 (затем используется в Airflow)

Ограничения по работе с новыми объявлениями и мультиязычными данными - новые объявления не имеют рейтинга, текстовые данные (отзывы, коммуникации и т.д) представлены на разных языках

#### Риски и открытые вопросы, фиксируем с первого дня

Т.к. для текущего среза отсутствует рейтинг, то таргет, не может быть арсчитан с учетом рейтинга. 
Поэтому модель будет обучаться на исторических объявлениях

Открыте вопросы 
- Способность модели предсказывать спрос на новых объявлениях без рейтинга?
- Как компенсировать отсутствие рейтинга для новых объявлений?
- Какие альтернативные признаки можно использовать?

Риски:
	Смещение модели (bias):
	- Модель обучается на данных с рейтингом, но должна работать и с объявлениями без рейтинга.
	- При прогнозе для нового жилья модель может давать неточные результаты из-за отсутствия ключевого признака.
	
	Низкая обобщающая способность:
	- Модель хорошо работает на знакомых данных (с рейтингом), но плохо — на новых (без рейтинга).
	- Это снизит точность прогнозов для свежих объявлений, которые критически важны для бизнеса.
	
	Риск неверной бизнес-стратегии:
	- Если прогнозы для новых объявлений окажутся неточными, компания может принять ошибочные решения.

Мультиязычные текстовые данные? Как обрабатывать текстовые признаки?

В рамках реализации скоринга объявлений на платформе объявлений аренты жилья необходимо предсказать будет ли высокий спрос на объявление.

**2.5. Модели для обучения.** Расскажите, какие модели и алгоритмы собираетесь привлечь для решения задачи, почему они вам подходят, какие гиперпараметры вы будете подбирать. Не забудьте построить модель baseline.

1. Baseline-модель:
	- Random Forest
	Устойчив к выбросам и нелинейным зависимостям.
	Не требует строгого масштабирования признаков.
	Хорошо работает в качестве «сильной» бейзлайн-модели перед бустингами.
	Подбираемые гиперпараметры:n_estimators: количество деревьев (100–300).
	max_depth: максимальная глубина дерева (для контроля переобучения).
	min_samples_split / min_samples_leaf: минимальное число объектов в узле/листе.

2.Основные алгоритмы и их обоснование
Градиентный бустинг (LightGBM / CatBoost) — Основной кандидат
Скорость и работа с памятью: LightGBM эффективен на больших датасетах (>600 тыс. строк).

Категориальные признаки: CatBoost и LightGBM нативно умеют обрабатывать категориальные переменные без необходимости раздувать матрицу признаков через One-Hot Encoding.
Устойчивость к пропускам: Бустинги самостоятельно обрабатывают NaN-значения, что критично для признаков календаря и отзывов.
Подбираемые гиперпараметры:
	- learning_rate (eta): шаг обучения (0.01–0.1).
	- num_leaves / max_depth: сложность структуры деревьев.
	- subsample / colsample_bytree: доли строк и признаков для сэмплирования (для борьбы с переобучением).
	- scale_pos_weight / auto_class_weights: балансировка классов, если таргет несбалансирован.

С точки зрения бизнеса ключевая задача — не допустить показа неактивных и некачественных объектов на приоритетных позициях. Поэтому приоритет отдается высокой точности (Precision).
Основная метрика оптимизации: PR-AUC на Stratified Cross-Validation (5 фолдов).
Вспомогательные метрики: ROC-AUC, Precision и F1-Score.

## 3. Сборка обучающей таблицы и целевой переменной

Раздел нужно заполнить в следующей части проекта. Здесь приведите описание ваших ключевых решений:
* как собирали таблицу;
* как считали медианы по сегментам (`city` + `room_type`);
* как рассчитали признак `is_high_demand`, какие колонки-источники целевой переменной удалили во избежание утечки данных.

**Как собирали таблицу.** Данные лежат в PostgreSQL (схема `final_project`) отдельно по каждому из 10 городов: `{city}_listings`, `{city}_calendars`, `{city}_reviews`.

* `listings`: таблицы всех городов объединены через `UNION ALL` с добавлением колонки `city`, получено 661 425 строк и 65 колонок. В таблицах несколько снимков одного объявления (отличаются цена, число отзывов, рейтинг), поэтому по ключу `(city, id)` оставлена одна строка, удалено 297 341 дубль. Итого 364 084 объявления. Идентификатор приведён к `BIGINT` на стороне БД, чтобы не потерять точность (float округляет длинные id).
* `calendars`: агрегация выполнена в БД на уровне объявления (доля доступных дней `calendar_availability_rate`, средние ограничения по ночам), 327 717 объявлений. Агрегат на стороне БД выбран, потому что полная календарная таблица очень большая.
* `reviews`: в БД для каждого объявления берутся 10 последних отзывов за год до последней даты отзывов города. Считаются средняя длина отзыва (`avg_recent_comment_len`) и склеенный текст (`concat_recent_comments`), 185 123 объявления.
* Таблицы соединены с `listings` по `id` через `LEFT JOIN`: объявления без календаря или отзывов остаются, пропуски сохраняются как `NaN`.

**Медианы по сегментам.** Для каждой пары `city` + `room_type` посчитаны медианы `numeric_of_reviews_ltm` (отзывы за год), `price` и `review_scores_rating` (пропуски при расчёте медианы игнорируются). Сегмент «город + тип жилья» выбран, чтобы сравнивать объявление с похожими, а не со всем рынком (цены и число отзывов в разных городах несопоставимы).

**Целевая переменная `is_high_demand`.** Рассчитаны `price_ratio = price / median_price` и `rating_ratio = rating / median_rating`. Целевая переменная равна 1, если одновременно:

* отзывов за год больше медианы сегмента;
* `price_ratio >= 1` (цена не ниже рынка);
* `rating_ratio >= 1` (рейтинг не ниже рынка);

и 0 во всех остальных случаях.

**Проблема пропусков.** У 81 561 объявления (22.4%) отзывов больше медианы, но цену или рейтинг сравнить нельзя, и они получали метку 0 только из-за `NaN`. Из-за этого доля класса 1 занижалась (5.46% против 7.04%). Эти объекты исключены из обучения. Итоговая выборка: 282 523 объявления, класс 1 составляет 19 876 (7.04%), класс 0 составляет 262 647. Объявления без отзывов за год остаются с меткой 0: условие «отзывов больше медианы» для них заведомо ложно, метка определена корректно.

**Защита от утечки данных.** Из признаков удалены все колонки, из которых считается цель: `numeric_of_reviews_ltm`, `price`, `review_scores_rating`, `median_reviews_ltm`, `median_price`, `median_rating`, `price_ratio`, `rating_ratio`. Идентификатор `id` и сырые даты удалены. Колонка `city` использовалась только для расчёта цели и в признаки не входит (географию модель получает из `latitude` и `longitude`). Из календаря исключены поля с фактической заполняемостью будущих дат (`calendar_booked_days_365`) и будущие цены. Для анализа качества по городам города сохраняются отдельно и в модель не передаются.

## 5. Признаки и обработка текста
**Итоговый набор:** 31 признак: 7 категориальных, 2 текстовых, 22 числовых.

* Категориальные: `room_type`, `host_response_time`, `host_is_superhost`, `host_identity_verified`, `instant_bookable`, `host_has_profile_pic`, `property_type_top`. Пропуски кодируются категорией `Missing`; `property_type_top` оставляет 20 самых частых типов жилья, остальные `Other`.
* Новые числовые признаки: `days_since_last_review`, `review_span_days`, `host_tenure_days` (даты переведены в количество дней), `calendar_closed`, `is_long_stay` (минимум от 28 ночей), `guests_per_bedroom`, `guests_per_bathroom`, `amenities_count` (число удобств по запятым, оценка приблизительная).
* Даты считаются относительно опорной даты. При обучении опорной датой служит последний отзыв города, при инференсе дата батча.

**Обработка текста.** Из названий (`name`) и склеенных свежих отзывов получены строки `filtered_name` и `filtered_sentences`. Шаги: нижний регистр, удаление знаков препинания и лишних пробелов, разбиение на слова, удаление стоп-слов. Отзывы многоязычные, поэтому использован список стоп-слов восьми языков (английский, французский, немецкий, испанский, нидерландский, итальянский, португальский, русский; 1 501 слово из NLTK). Пропуски в тексте заменяются пустой строкой.

**Кодирование.** Масштабирование не применяется: все модели древовидные. Для Random Forest и LightGBM категории кодируются `OrdinalEncoder`, текст `TfidfVectorizer(max_features=100)` отдельно для каждого текстового признака. Для CatBoost категории передаются строками, текст как `text_features` (нативная обработка). Пропуски в числовых признаках оставлены: в Random Forest,LightGBM они заполняются `-1` как маркер «нет данных» внутри пайплайна, в CatBoost остаются `NaN`. Преобразования обучаются только на обучающей выборке (внутри пайплайна на каждом фолде).

Значения почти совпадают с кросс-валидацией (PR-AUC 0.657, F1 0.613), признаков переобучения нет. Из 3 975 объявлений с высоким спросом модель находит около 69%, при этом около 55% её срабатываний верны (примерно в 8 раз лучше случайного выбора).

**SHAP-анализ.** Самые важные признаки: `avg_recent_comment_len` (средний |SHAP| 1.96), `beds` (1.59), `review_span_days` (1.04), `days_since_last_review` (0.93), `filtered_name` (0.87). Высокий спрос связан со свежими и содержательными отзывами, недавней активностью и большим числом кроватей. Отсутствие отзывов и данных о кроватях сильно снижает оценку.

**Что это значит для бизнеса.** На спрос больше всего влияет актуальность объявления: наличие свежих отзывов и заполненность карточки. Для листингов с низким скором полезно запрашивать отзывы, заполнять характеристики жилья и обновлять объявление. Модель подходит для приоритизации листингов, а не для автоматических решений.

**Ограничения.**

* Около 45% срабатываний ложные (Precision 0.55), около 31% реальных объектов с высоким спросом пропускается.
* Цель определяется через число отзывов. Для объявлений без свежих отзывов (новых) модель работает хуже.
* Из обучения исключены 22% объявлений без цены, их качество не оценивалось.
* Город не используется как признак, качество по отдельным городам не проверялось.
* Опорная дата для признаков дат при обучении (последний отзыв города) отличается от даты батча при инференсе.
* Модель обучена на одном срезе данных, при изменении данных необходим мониторинг.
